# 추적표

> 요약: 요구사항 ↔ 기능 ↔ 화면 ↔ 검증 항목을 한 표로 연결하고, 빈 칸과 누락을 드러내는 추적표를 만든다.
> 산출물: crewgenai-output/docs/08-traceability.md

## 언제 쓰나

- 03~07 문서가 갖춰진 뒤 요구가 기능·화면·검증까지 이어졌는지 확인할 때
- 개발·테스트 착수 전에 누락된 요구나 근거 없는 기능을 찾을 때
- 요구 변경이 생겨 영향을 받는 기능·화면·검증 항목을 찾아야 할 때
- 고객 검수·내부 품질 점검에서 요구 충족 여부를 설명해야 할 때

## 운영 탭에 붙여넣을 지시문

```text
목표: {{제품명}}의 요구사항-기능-화면-검증 추적표를 작성한다. 결과는 crewgenai-output/docs/08-traceability.md 한 파일이다.
읽을 자료: crewgenai-output/docs/03-customer-requirements.md, 05-features-core-sub.md, 06-screen-definition.md, 07-content-description.md(모두 crewgenai-output/docs/ 아래), {{테스트·검증 자료 경로}}(있으면). 이 경로 밖의 자료는 인용하지 않는다.
담당 배정: 00 총괄이 계획, 12 평가·회귀가 검증 항목(TC) 작성, 11 관제·추적이 ID 대조, 15 통합 품질·결과물이 누락 점검과 형식 점검을 맡는다.
필수 섹션(이 순서): 1 문서 정보, 2 대상 문서와 버전, 3 전체 추적표, 4 검증 항목 목록, 5 누락·불일치 목록, 6 커버리지 요약, 7 근거 목록, 8 사용자 결정 필요 항목, 9 확인 필요 항목.

- 각 문서의 ID(REQ-xxx, FN-xxx, SCR-xxx, CT-xxx)는 원문서에 있는 것만 쓴다. 새 ID를 만들거나 바꾸지 않는다.
- 검증 항목은 TC-001부터. 05 문서의 수용 기준을 근거로 만들고, 각 TC에 관련 REQ·FN, 확인 방법, 기대 결과, 실행 상태를 적는다.
- 실행 상태는 미실행/통과/실패 중 하나만 쓴다. 실행 기록(파일경로:줄번호)이 없으면 반드시 미실행이다.
- 연결이 없는 칸은 비워 두지 않고 "누락"으로 쓰고 5절에 등록한다. 한쪽에만 있는 ID, 폐기된 ID 참조, 이름 불일치도 5절에 적는다.
- 커버리지 수치는 표에서 직접 센 값만 쓰고 계산식(분자/분모)을 함께 적는다.
완료 기준:
- 9개 섹션이 모두 있다. 03 문서의 모든 REQ가 3절에 한 행 이상 있다.
- 3절에 빈 칸이 없고, 모든 "누락"이 5절에 있다.
- 통과로 표시된 TC는 모두 실행 기록 출처가 있다.
결과 파일 경로, REQ·FN·SCR·TC 수, 누락 건수를 마지막 보고에 적는다.
```

## 문서 구성(산출물 목차)

1. 문서 정보 — 제품명, 작성일, 버전, 작성 기준 시점
2. 대상 문서와 버전 — 표: `문서 | 파일경로 | 버전·수정일 | ID 범위`
3. 전체 추적표 — 표: `REQ ID | 요구 요약 | 우선순위 | FN ID | SCR ID | CT ID | TC ID | 실행 상태 | 비고`
4. 검증 항목 목록 — 표: `TC ID | 관련 REQ | 관련 FN | 관련 SCR | 확인 방법(수동/자동) | 사전 조건 | 절차 요약 | 기대 결과 | 실행 상태 | 실행 기록`
5. 누락·불일치 목록 — 표: `번호 | 유형(요구→기능 누락/기능→화면 누락/검증 누락/근거 없는 기능/ID 불일치/폐기 ID 참조) | 관련 ID | 내용 | 영향 | 조치 제안`
6. 커버리지 요약 — 표: `구분 | 분자 | 분모 | 비율 | 비고` (예: 기능 연결된 필수 REQ, 검증 항목 있는 FN, 통과한 TC)
7. 근거 목록 — 표: `번호 | 파일경로:줄번호 | 내용 요약`
8. 사용자 결정 필요 항목 — 표: `번호 | 결정할 내용 | 선택지 | 영향 | 결정 기한`
9. 확인 필요 항목 — 표: `번호 | 확인할 내용 | 확인 방법 | 관련 ID`

## 작성 규칙

- 근거: 모든 ID는 원문서에서 확인한 것만 쓰고, 연결 관계마다 원문서의 `(파일경로:줄번호)`로 확인할 수 있어야 한다.
- 빈 칸 금지: 연결이 없으면 "누락", 해당 없으면 "해당 없음(사유)"를 쓴다.
- ID 체계: `REQ-001`, `FN-001`/`FN-001-1`, `SCR-001`, `CT-001`, `TC-001`. 원문서 ID를 수정하지 않는다. 수정이 필요하면 5절에 조치 제안으로 적는다.
- 실행 상태: `미실행`/`통과`/`실패`만 쓴다. 계획이나 코드 존재를 통과로 쓰지 않는다.
- 숫자: 커버리지는 분자·분모·비율(%)을 모두 적고 소수점 첫째 자리까지 쓴다.
- 한 REQ가 여러 FN·SCR에 연결되면 행을 나누어 쓴다.

```text
맥락:
- 제품명: {{제품명}}
- 요구사항 정의서: {{03-customer-requirements.md 경로 또는 내용}}

- 화면 정의서: {{06-screen-definition.md 경로 또는 내용}}
- 콘텐츠 설명서: {{07-content-description.md 경로 또는 내용}}
- 테스트·검증 기록(있으면): {{테스트·검증 자료 경로}}

과제: 요구사항 ↔ 기능 ↔ 화면 ↔ 검증 항목 추적표를 Markdown으로 작성한다.

제약:
- 원문서에 있는 ID만 쓴다. 새 ID를 만들거나 기존 ID를 바꾸지 않는다. 단, 검증 항목은 TC-001부터 새로 붙인다.
- TC는 기능 명세의 수용 기준에서 만들고 관련 REQ·FN·SCR을 적는다.
- 실행 상태는 미실행/통과/실패만 쓴다. 실행 기록이 없으면 미실행이다.
- 빈 칸을 두지 않는다. 연결이 없으면 "누락"으로 쓰고 누락·불일치 목록에 올린다.
- 커버리지 수치는 직접 센 값만 쓰고 분자·분모를 함께 적는다.

출력 형식(이 목차 순서):
1 문서 정보 / 2 대상 문서와 버전 / 3 전체 추적표 / 4 검증 항목 목록 /
5 누락·불일치 목록 / 6 커버리지 요약 / 7 근거 목록 /
8 사용자 결정 필요 항목 / 9 확인 필요 항목

진행 순서:
1. 각 문서에서 ID 목록과 문서 간 참조 관계를 모두 뽑는다.
2. REQ 기준으로 FN·SCR·CT를 연결해 전체 추적표를 만든다.
3. 수용 기준으로 TC를 만들고 실행 기록과 대조해 실행 상태를 정한다.
4. 역방향(FN→REQ, SCR→FN)도 대조해 근거 없는 기능·화면과 ID 불일치를 찾는다.
5. 커버리지를 세고 스스로 점검한다.
   - 모든 REQ가 표에 있는가
   - 빈 칸이 남아 있는가
   - 실행 기록 없이 통과로 쓴 TC가 있는가
   - 수치가 표와 일치하는가
6. 마지막에 사용자에게 물어볼 질문 목록(최대 5개, 중요도 순)을 붙인다.

정보가 부족하면 추측하지 말고 질문 목록을 먼저 제시하라. 요구사항 정의서나 기능 명세서가 없으면 추적표 대신 필요한 문서 목록과 질문만 돌려준다.
```
